# 导航目标与 RL 输入的闭环接线

操作流程保持为：E 左档，在 APP 地图选目标，点一次“开始导航”。工作台自动完成规划、接管零速握手和开始执行，不增加人工确认、验收文件或标定文件门。E 中档暂停、E 右档手动、摇杆接管、取消和障碍零速保持原语义。

本次候选修复的是速度接口：原接线把导航的 m/s、rad/s 目标直接写入策略观察量。实际记录中非零前进输入最高约 0.04025，控制器已接管且没有输入拦截，但相同策略在隔离模型回放中基本停在原地。策略输入不能冒充实测机身速度。

`SpeedResponse` 在原生步态循环内使用实测速度闭环生成策略观察输入，不加载隔离模型的逆响应曲线。启动时逐渐搜索可产生运动的输入；持续观察到运动后使用 PI 跟踪。目标为零、导航不再拥有控制权或反馈过期时直接清空输出及积分。内部策略输入范围是控制器候选参数，不是 m/s 目标范围或真实运动性能保证。倍率仍先作用于导航目标；半速前进目标上限保持 0.075 m/s，偏航保持 ±0.12 rad/s。

协议保留原目标帧与租约，增加同一连接上的 `MEASURED_VELOCITY` 操作；其回执附带目标、实测速度、策略输入、原始反馈时间及有效状态。原生调用方仍从 `step()` 取得控制权和目标，导航分支从 `policy_state()` 取策略观察输入。手动分支沿用原映射。双方必须使用配套协议实现；这不是新增的用户操作步骤。

反馈来自已有雷达里程计的因果速度估计。接收 ROS 消息时将其原始源年龄转换到本机单调时钟，后续状态消息、RPC 和步态 tick 不刷新该时间。源时间仍按既有 500 ms 过期；这不意味着设备采样时钟已经同步。该候选没有新增机身关节运动学数据，也没有把雷达参考系改称已标定机身系。

工作台会在私有 runtime 中自动保存 `gait-velocity.private.jsonl`：原始、缓冲、平滑、避障后的指令，最终目标，以及原生回执的实测速度和策略输入。记录器使用独立线程与有界队列，两个轮换文件，每个约 8 MiB；记录故障不改控制输出。原始接收时间仅用于诊断阶段延迟，不能冒充消息源时间。

验证范围：Python 回归、原生控制权测试、真实 Unix socket 的配对收发及 ARM check-only。隔离模型中，带 100 ms 延迟、10 Hz、400 ms 均值反馈时，0.075 m/s 目标的后段均值约 0.07659 m/s，0.0125 m/s 约 0.01074 m/s；取消、障碍零速、E 右档、摇杆介入和速度源过期均撤回策略导航输入。

失败保留：原地转向仍带有约 0.0091 m/s 的模型前向漂移；1 m 合成直线目标第一次进入停止带后，最终模型净位移为 0.9061 m，未通过本次试验的 8 cm 最终误差比较。这些比较参数属于此次试验，不是用户规定的开走条件。该试验没有执行地图规划或实际障碍绕行，不能据此宣称完整导航、窄门或实机行走通过。启动阶段也仍有瞬态速度偏差，后段均值不代表全程速度上界。

此版本为候选代码：1006 的独立 ARM 程序已构建和检查，未替换故障中的生产步态/驱动，尚无这版的真实运动验收。原 EtherCAT 故障由驱动开发另行修复；不能用新导航接口掩盖已经退出的电机驱动。
